# Spec: Clear the chat history on Android

The owner approved the intent with its proposed answers:
- Clear chat acts on one computer;
- per-entry Delete is in this issue, and it keeps text selection;
- no confirmation dialog;
- Clear chat also empties the clipboard, but only when it still holds the
  clip Flux received from this computer;
- abandoned resumable transfers are a separate issue;
- unit tests, then the phone test with the #13 setup.

Paths are under `android/app/src/main/java/org/omarchy/flux/` unless
they start with `android/app/src/test/` or `gui/`.

## Design

### 1. The log (`core/SendLog.kt`)

Two pure functions next to `addSend` (`SendLog.kt:70-83`), so the tests
can call them without the object:

```kotlin
/** Drops the ended entries of the computer [deviceId]. Running files stay, so their progress and end still find them. */
fun clearSends(list: List<SendEntry>, deviceId: String): List<SendEntry> =
    list.filter { it.deviceId != deviceId || it.state == TransferState.Running }

/** Drops the entry [id] when it has ended. A running file stays. */
fun removeSend(list: List<SendEntry>, id: Long): List<SendEntry> =
    list.filter { it.id != id || it.state == TransferState.Running }
```

Two calls in `object SendLog`, after `fileResumed` (`SendLog.kt:203-211`),
in its style:

```kotlin
/** Drops the ended entries of the computer [deviceId], and returns how many of its files still run. */
fun clear(deviceId: String): Int {
    var running = 0
    _entries.update { list ->
        clearSends(list, deviceId).also { kept -> running = kept.count { it.deviceId == deviceId } }
    }
    return running
}

/** Drops the ended entry [id]. */
fun remove(id: Long) {
    _entries.update { removeSend(it, id) }
}
```

- Both go through `_entries.update`, like every other writer
  (`SendLog.kt:143,176,195,200,206`). The running check and the count run
  on the list that the successful update wrote. A concurrent add,
  progress, end or resume is never lost, and an entry that `fileResumed`
  just set running again stays.
- The id counter `ids` (`SendLog.kt:136`) doesn't change, so ids stay
  unique and the transfer callbacks keep finding their entries.

### 2. Which clip is on the clipboard (`core/Plugins.kt`, `core/ClipImage.kt`)

The log can't say what is on the clipboard: it cuts text at 400
characters (`SendLog.kt:150`), keeps one incoming clip for all computers
(`SendLog.kt:90-91`), and can roll the clip out (`SendLog.kt:71-83`). So
the clipboard check uses what Flux already keeps for echo suppression,
plus the computer:

- `Plugins.lastRemoteClip` holds the whole last text a computer put on the
  clipboard (`Plugins.kt:24,186`). Add next to it:
  ```kotlin
  /** The device ID of the computer that sent [lastRemoteClip]. */
  @Volatile var lastRemoteFrom: String? = null
  ```
  `putRemoteText` (`Plugins.kt:181`) gets a `deviceId: String` parameter
  and sets `lastRemoteFrom = deviceId` before `lastRemoteClip = text`. Its
  three callers pass the id they already have: `Plugins.kt:174` (`d.id`),
  `Share.kt:106` (`d.id`), and Copy on a received clip,
  `ui/ChatScreen.kt:663` (`e.deviceId`).
- `ClipImage.lastRemote` holds the address of the last image a computer
  put on the clipboard (`ClipImage.kt:38,83`). Add next to it
  `@Volatile var lastRemoteFrom: String? = null`, set to `d.id` before
  `lastRemote = uri`.

A pure check, testable without Android, top-level in `core/Plugins.kt`:

```kotlin
/**
 * True when the clip on the clipboard is the last one that the computer
 * [deviceId] sent: Flux's label, and the same whole text or image address.
 */
internal fun isRemoteClip(
    label: String?, text: String?, uri: String?, deviceId: String,
    remoteText: String?, textFrom: String?, remoteImage: String?, imageFrom: String?,
): Boolean = label == "Flux" && (
    (text != null && text == remoteText && textFrom == deviceId) ||
        (uri != null && uri == remoteImage && imageFrom == deviceId)
    )
```

Two helpers in `core/Android.kt`, after `setClipboardImage`
(`Android.kt:165-169`):

```kotlin
/** True when the clipboard holds the last clip that the computer [deviceId] sent. It needs the focus. */
fun holdsClipFrom(context: Context, deviceId: String): Boolean {
    val cm = context.getSystemService(ClipboardManager::class.java) ?: return false
    val clip = runCatching { cm.primaryClip }.getOrNull()?.takeIf { it.itemCount > 0 } ?: return false
    val item = clip.getItemAt(0)
    return isRemoteClip(
        clip.description.label?.toString(), item.text?.toString(), item.uri?.toString(), deviceId,
        Plugins.lastRemoteClip, Plugins.lastRemoteFrom, ClipImage.lastRemote?.toString(), ClipImage.lastRemoteFrom,
    )
}

/** Empties the clipboard. It returns false when Android refuses. */
fun clearClipboard(context: Context): Boolean {
    val cm = context.getSystemService(ClipboardManager::class.java) ?: return false
    return runCatching { cm.clearPrimaryClip() }
        .onFailure { android.util.Log.w("FluxClipboard", "clearing the clipboard failed", it) }
        .isSuccess
}
```

- The text must be the whole text the computer sent, not a cut or a
  prefix. Flux's other copies with the "Flux" label, such as a command
  (`ui/TiledKit.kt:636`) or an SSH key (`ui/SshKeyScreen.kt:115`), don't
  match. A copy from another app has another label.
- A newer clip from another computer replaces `lastRemoteClip` or
  `lastRemote` and its `lastRemoteFrom`. So the older computer no longer
  owns the clipboard, and its Clear leaves it.
- Copy on the received clip puts the same text back
  (`ChatScreen.kt:662-667`). It is still that computer's clip, so it
  matches; that is intended.
- The check doesn't use the log, so it still works after the clip rolled
  out of it.
- `clearPrimaryClip` exists from API 28; `minSdk` is 29
  (`android/app/build.gradle.kts:39`).
- **What a clear sets off.** It fires Flux's clipboard listener
  (`FluxApp.kt:18`). `sendClipboardToAll` finds no image and no text and
  returns before sending or touching the echo state
  (`Plugins.kt:269,296-305`). The dock's listener reads no description
  and shows no clip (`ChatScreen.kt:1118,1127`).
- **Order.** Flux posts its clipboard writes to the main thread
  (`Plugins.kt:189-191`, `ClipImage.kt:85`) right before or right after it
  adds the entry (`Plugins.kt:174`, `ClipImage.kt:84`). Clear and Delete
  run on the main thread from a tap. A tap that saw the entry comes after
  the write in the main queue, so the write has run.

### 3. Clear chat (`ui/ChatScreen.kt`)

`ComputerMenu` (`ChatScreen.kt:244-269`) gets an `onClear: (() -> Unit)?`
parameter. When it isn't null, the menu adds a last item:

```kotlin
if (onClear != null) Triple("Clear chat", Ic.delete, onClear) else null,
```

`Ic` gets `val delete = R.drawable.ic_delete` (`ui/Icons.kt`). The
drawable `res/drawable/ic_delete.xml` exists, and nothing uses it today.

`ComputerChatScreen` passes it (`ChatScreen.kt:212`), with
`val context = LocalContext.current`:

```kotlin
val clearable = entries.any { it.state != TransferState.Running }
ComputerMenu(d, actions, onClear = if (clearable) ({ clearChat(context, d.id) }) else null)
```

So the item shows only when the chat has something to clear, as the
desktop's Clear button does (`gui/qml/pages/Chat.qml:232`).

```kotlin
/** Clears the chat of the computer [id], and the clipboard when it still holds the last clip from it. */
private fun clearChat(context: Context, id: String) {
    if (isDemo(id)) return FluxCore.toast("This is a sample computer")
    val clip = Android.holdsClipFrom(context, id)
    val running = SendLog.clear(id)
    val cleared = clip && Android.clearClipboard(context)
    FluxCore.toast(
        (if (cleared) "Chat and clipboard cleared" else "Chat cleared") +
            if (running > 0) ". Files in progress stay." else "",
    )
}
```

- The toast says the clipboard was cleared only when it really was.
- A sample computer gets the same toast as the other chat actions on it
  (`ChatScreen.kt:874,879`); its sample entries come from
  `DebugInbox.sends()` (`ChatScreen.kt:150`), not from the log.
- Other computers' entries stay, because `clearSends` keeps every entry
  of another `deviceId`.
- The chat and the Chats list both read `SendLog.entries` through
  `rememberChatLog()` (`ChatScreen.kt:146-151`, `ChatsScreen.kt:104-108`),
  so both update at once, and search (`core/ChatList.kt:121`) no longer
  finds the removed entries.
- Open approvals come from `Approvals.current` (`ChatScreen.kt:198-201`)
  and stay.

### 4. Delete one entry (`ui/ChatScreen.kt`)

The thread wraps each log entry (`ChatScreen.kt:392`):

```kotlin
is ChatLogItem -> EntryMenu(c.entry, context) { onText -> LogEntry(c.entry, context, onText) }
```

```kotlin
/**
 * An entry with Delete. A long press on the entry opens a menu where the
 * finger is. A long press on text that can be selected selects it, as
 * before. TalkBack reads the entry as 1 item with Delete in its actions.
 * A running file has no Delete.
 */
@Composable
private fun EntryMenu(e: SendEntry, context: Context, content: @Composable (onText: (LayoutCoordinates) -> Unit) -> Unit) {
    if (e.state == TransferState.Running) return content {}
    var at by remember { mutableStateOf<IntOffset?>(null) }
    var self by remember { mutableStateOf<LayoutCoordinates?>(null) }
    var text by remember { mutableStateOf<LayoutCoordinates?>(null) }
    val delete = { deleteEntry(context, e) }
    Box(
        Modifier
            .onGloballyPositioned { self = it }
            .pointerInput(e.id) {
                detectTapGestures(onLongPress = { p ->
                    // The selectable text keeps its own long press.
                    val box = text?.let { t -> self?.localBoundingBoxOf(t) }
                    if (box == null || !box.contains(p)) at = IntOffset(p.x.toInt(), p.y.toInt())
                })
            }
            .semantics(mergeDescendants = true) {
                customActions = listOf(CustomAccessibilityAction("Delete") { delete(); true })
            },
    ) {
        content { text = it }
        at?.let { p ->
            Box(Modifier.offset { p }) {
                DropdownMenu(expanded = true, onDismissRequest = { at = null }) {
                    DropdownMenuItem(text = { Text("Delete") }, leadingIcon = { Sym(Ic.delete) }, onClick = {
                        at = null
                        delete()
                    })
                }
            }
        }
    }
}

/** Deletes the entry [e], and empties the clipboard when it is the clip from that computer that is still on it. */
private fun deleteEntry(context: Context, e: SendEntry) {
    if (isDemo(e.deviceId)) return FluxCore.toast("This is a sample computer")
    val clip = e.incoming && (e.kind == SendKind.Clip || e.kind == SendKind.ClipImage) && Android.holdsClipFrom(context, e.deviceId)
    SendLog.remove(e.id)
    if (clip) Android.clearClipboard(context)
}
```

`LogEntry` (`ChatScreen.kt:583-592`) gets `onText: (LayoutCoordinates) -> Unit`
and passes it to `SentBubble` (`ChatScreen.kt:699-712`), which sets
`Modifier.onGloballyPositioned(onText)` on its `SelectionContainer`'s
text. The other entries have no selectable text and ignore it.

- **Long press, not a visible button.** It is the Android convention for
  a message's actions, and it adds nothing to each bubble.
- **Text selection stays.** A long press inside the text of a sent bubble
  doesn't open the menu, so the `SelectionContainer` (`ChatScreen.kt:702`)
  selects as today. Outside the text (the meta line, the space beside the
  bubble, any card, file or photo) a long press opens the menu.
- **The menu opens where the finger is**, through a zero-size anchor at
  the press. A full-width anchor would open it at the left edge, away
  from right-aligned bubbles (`ChatScreen.kt:700,720,758`).
- **Taps.** `detectTapGestures` with only `onLongPress` lets a short tap
  through to Open and Copy. A long press on Open or Copy opens the menu
  and still runs the action on release (Risks).
- **Scroll.** A drag cancels `detectTapGestures`, so scrolling the thread
  opens no menu.
- **TalkBack.** `mergeDescendants = true` makes the entry one focusable
  item that carries the Delete action. The card's top row already merges
  into one line (`ChatScreen.kt:464`). Open and Copy are clickable, so
  they stay their own items.
- **No toast** after a Delete, as on the desktop (`ChatEntry.qml:197`).
  The entry disappearing is the feedback.
- **Clipboard:** see the owner decision below.
- Approval cards, pair cards and other `ChatEventItem`s
  (`ChatScreen.kt:393-397`) aren't log entries and get no Delete.

### 5. What doesn't change

- The protocol, `fluxd`, the desktop, iOS and macOS.
- `addSend`, `addClipIn`, `progressSend`, `endSend`, `resumeSend`.
- `ResumableTransfer`. A deleted failed transfer that the computer retries
  appears again as a new entry (`ResumableTransfer.kt:57-61`), as the
  intent says.
- The echo check (`Plugins.kt:307`), which still reads `lastRemoteClip`.
- `InboxFeed.clip`, the pending clip, the cached clipboard image file and
  notifications. They aren't shown in the chat (intent, Facts).

## Owner decision

1. **Does Delete on the received clip also empty the clipboard?** The
   intent names the clipboard step for Clear chat only. Proposed: yes, by
   the same rule (Design 4). Deleting a password's entry while the
   password stays in the clip row below would not do what the user meant.
   Both reviewers agree.

## Alternatives rejected

- **A Clear for all computers on the Chats list.** The owner chose one
  computer. Can come later.
- **A confirmation dialog.** The owner chose none; the desktop has none.
- **Clear by setting `_entries.value`.** A snapshot written back could
  drop a concurrent add, progress or end. `update` retries on a race.
- **Dropping running transfers too.** Their progress and end updates
  would find nothing, and the chat would lose the file's card.
- **Matching the clipboard against the log entry.** The entry's text is
  cut at 400 characters, the log keeps one incoming clip, and the entry
  can roll out. A prefix match could empty a different text.
- **Matching an image by `ClipImage.lastRemote` alone.** It doesn't say
  which computer sent it.
- **Matching by the clipboard's timestamp.** Android hides the clipboard
  from an app without focus, so Flux can't read the time when a clip
  arrives in the background.
- **Emptying the clipboard whenever its label is "Flux".** Flux also uses
  that label for its own copies of commands and keys.
- **Always emptying the clipboard on Clear.** The clipboard can hold
  something the user copied in another app.
- **Replacing `SelectionContainer` with a Copy and Delete menu.** It
  removes partial selection of sent text, which the intent keeps.
- **A long press on the whole entry, text included.** Both the
  `SelectionContainer` and the parent's detector see the same press and
  time out together, so the menu would open over the selection.
- **A long press on the meta line only.** An 11 sp line is far below a
  48 dp touch target.
- **A Delete icon on each bubble.** It adds clutter to every entry on a
  narrow screen. The desktop shows its icons on hover; a phone doesn't
  hover.
- **Swipe to delete.** It conflicts with the thread's scroll and the
  system back gesture, and is easy to trigger by accident.
- **Marking Flux's clipboard writes as sensitive.** A separate issue, as
  the intent says.

## Risks

- **A long press on Open or Copy** opens the menu, and the button's click
  still fires on release. Copy puts the same clip back; Open opens the
  file. Accepted: harmless, and a short tap is the normal use.
  Verification 2.5 checks it doesn't do more.
- **The text bounds.** If `localBoundingBoxOf` misreports the text's box
  (for example during a scroll), a press can land on the wrong side of the
  check: the menu opens on text, or not beside it. Verification 2.5 checks
  both at the top and bottom of a scrolled thread.
- **TalkBack merging.** Merging puts the sent text and the meta line in
  one item, so TalkBack can't select part of a sent text. TalkBack has no
  partial selection in a chat bubble today either. Verification 2.6
  checks that Open, Copy and Delete are each reachable.
- **A clipboard read without focus.** Clear chat and Delete run from a
  tap in Flux, which has focus. If the read still fails, `holdsClipFrom`
  is false: the chat is cleared, the clipboard stays, and the toast says
  "Chat cleared".
- **Other apps' clipboard listeners** (keyboards, clipboard managers) see
  an empty clip, as on any clear. A clipboard manager can keep its own
  copy; that is outside Flux.
- **The computer's clipboard.** Clearing the phone doesn't clear the
  computer, and its next sync can bring the same text back as a new clip.
  That is the computer's history, out of scope.
- **Stuck resumable transfers** stay `Running` and survive Clear, as the
  intent accepted. The toast then says files in progress stay.

## Verification

1. `./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug`
   in CI (`build.yml`). New tests:
   - `SendLogTest`:
     - `clearSends` drops this computer's done and failed entries, and
       keeps its running file and every entry of another computer;
     - after `clearSends`, `progressSend` and `endSend` on the running
       file still update it;
     - `removeSend` drops a done entry, keeps a running one, and changes
       nothing for an unknown id;
     - a failed file removed, then started again, gets a new id that
       doesn't collide.
   - `ChatListTest`: after `clearSends`, `chatList` with a query that
     matched the removed text finds nothing, and the computer's row has no
     last entry.
   - A new `RemoteClipTest` for `isRemoteClip`: the same text from the
     same computer matches; another label, another computer, a text that
     differs only after 399 characters, a 400-character text, and a
     prefix don't; an image matches by address and computer only; text
     and image fields don't cross.
   - `holdsClipFrom` and `clearClipboard` need a real clipboard;
     Verification 2 covers them.
2. **Phone**, with the #13 setup (`fluxd` on p620, paired) and the
   branch's debug APK:
   1. Copy a line on the computer with clipboard sync on. It shows in the
      chat and in the clip row as "Clipboard from <computer>".
   2. Send a large file from the computer, and while it is received,
      Clear chat. The clip is gone from the thread, the Chats list and the
      clip row. The toast says "Chat and clipboard cleared. Files in
      progress stay." The file keeps its progress and ends with its card.
   3. Copy something in another app, then Clear chat again after a new
      entry. The other app's clip stays, and the toast says "Chat
      cleared".
   4. Sync a clip, then long press its card and Delete: the card and the
      clip row's clip are gone. Sync a clip, copy in another app, Delete
      the card: the other app's clip stays.
   5. Send a text and a link from the phone. Long press beside each
      bubble and on a received file's card: the menu opens at the finger,
      and Delete removes only that entry. Long press the text of a sent
      bubble, at the top and at the bottom of a scrolled thread: text
      selection starts and no menu opens. Scroll the thread: no menu
      opens. Tap Open on a received file and Copy on a received clip: they
      work as before. Long press Copy: the menu opens and nothing else
      happens beyond the copy.
   6. With TalkBack on, each entry is one item with Delete in its
      actions, and Open and Copy are still reachable.
   7. The menu has no Clear chat on an empty chat.
   8. In a debug build, Clear chat and Delete on a sample computer show
      "This is a sample computer". Isolation between two real computers
      is covered by `SendLogTest`; if a second computer is paired, check
      its chat is unchanged after step 2.
3. `nix flake check path:.`.
