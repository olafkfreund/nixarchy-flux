# Spec: Text messages: no false "Not sent", no hidden stale thread

The owner approved the intent with its proposed answers:
- item 2: fix only what the Pixel test or a unit test confirms, and fix the
  hidden reload error in any case; no list request on connect;
- item 1: no sent intents; fix the clock and capability cases. At the spec
  review the owner chose to keep the red **Not sent** label for both "no
  report in 60 s" and "the phone stored it as failed" (part 1);
- show MMS download notices only if the Pixel shows one;
- decline MMS media for now;
- close #25 when each item has a recorded result;
- the Pixel test with the #13 setup.

Parts 2-4 are unconditional. Part 5 lists fixes that ship only when the

## Design

### 1. The "Not sent" label stays (owner's decision)

No change. The window keeps the red **Not sent** for an outbox entry that
the phone didn't report in 60 s (`internal/core/sms.go:350-363`) and for a
message the phone stored as failed (`sms.go:131-140`), as
`docs/troubleshooting.md:287-289` already describes. Parts 2 and 3 remove
the causes of a false **Not sent** that fluxd can fix.

### 2. The phone's clock in each message packet

A report whose time is more than 120 s before the entry never matches
(`sms.go:42-45,382`). The fix measures the phone's clock instead of
widening the slack, which would let an older message with the same text
clear a new entry (the case `sms_test.go:399-408` guards).

- **Android** (`android/.../core/Sms.kt:125-133`, `packet`): add the
  phone's time in milliseconds to every `flux.sms.messages` packet:

  ```kotlin
  add("now" to System.currentTimeMillis())
  ```

  `packet` is the only builder (`messages` and `messagePackets` call it), so
  answers and live reports both carry it.
- **fluxd** (`sms.go:180-192`, the body of `handleSms`): decode it, and
  use it only when the phone is behind by more than the slack:

  ```go
  // Now is the clock of the phone when it sent the packet, in
  // milliseconds. An older phone leaves it out.
  Now int64 `json:"now"`
  ...
  // behind is how far the clock of the phone is behind this computer, in
  // seconds. A smaller gap, or a phone ahead, is left to smsClockSlack, so
  // the link delay and a clock that jumps ahead don't move the times.
  var behind int64
  if b.Now > 0 {
      if s := time.Now().Unix() - b.Now/1000; s > smsClockSlack {
          behind = s
      }
  }
  ```

  The call at `sms.go:229` becomes `confirmOutboxLocked(dev, msgs, behind)`.
  `confirmOutboxLocked` (`:368-375`) passes it on through a closure,
  because `slices.ContainsFunc` takes a one-argument function:

  ```go
  return slices.ContainsFunc(msgs, func(m SmsMessage) bool { return e.reportedBy(m, behind) })
  ```

- `reportedBy` (`sms.go:381-389`) compares on the computer's clock:

  ```go
  if !m.Outgoing || m.Time+behind < e.Time-smsClockSlack || !sameSmsText(m.Body, e.Body) {
  ```

- What this changes:
  - A phone up to 120 s behind, or any amount ahead: `behind` is 0, and
    matching is exactly as today. The link delay never moves a time.
  - A phone more than 120 s behind: times move by the measured gap, which
    includes the link delay `D`. An older message with the same text
    matches only when it is less than `120 + D` seconds older than the
    entry on the computer's clock, the same window as today plus `D`.
  - An older phone sends no `now`, and matching is as today.
- No other field changes. An older fluxd ignores `now`.
- The comment of `smsClockSlack` (`sms.go:42-45`) says it covers the
  link and a small clock gap; a larger gap uses `now`.

### 3. Refuse a send to a phone that doesn't offer text messages (`internal/core/sms.go`)

`SendSms` (`sms.go:284-318`) checks the capability before it adds an
outbox entry. The phone lists `flux.sms.messages` only while Text messages
is on and SMS access is granted (`android/.../protocol/Identity.kt:149-155,226-227`),
and the window already uses the same check to show Messages
(`internal/core/device.go:167-172,245`):

```go
d.mu.Lock()
// A device gets its features from its identity when it connects
// (device.go:160-172), so an offline device has none yet. It gets the
// offline error from d.send.
off := dev.link != nil && !dev.supports(proto.TypeSmsMessages)
name := dev.Name
sub := conversationSim(dev.conversations, clean)
d.mu.Unlock()
if off {
    return apiErr("not_supported", "%s does not share text messages. Turn on Text messages in Computers > Sync on the phone", name)
}
```

- The code is `not_supported`, the code `docs/ipc.md:296` gives for "the
  device cannot do the request".
- The check comes before the group check (`sms.go:302-304`), so the group
  error, which reads `dev.Name` outside the lock today, uses `name` too.
- `TestSendSmsLength` (`sms_test.go:296-306`) and `TestSmsOutboxLimits`
  (`:466-473`) send to a device with no link and still get `offline`.

So `flux-cli sms` to a phone with the switch off fails at once, instead of
leaving an entry that fails after 60 s. The window doesn't show Messages
for such a phone, so only the CLI and IPC callers see the error.

### 4. Show a failed reload of an open thread (`gui/qml/pages/Messages.qml`)

Today `loadError` shows only when the thread has no messages yet
(`Messages.qml:515`). A failed reload of a loaded thread sets `loadError`
(`:146-150`) and nothing shows it.

- The error line above the message field (`sendErrorLine`, `:537-551`)
  becomes a row that also shows a reload error of the loaded thread, with
  a **Retry** button:

  ```qml
  readonly property string staleError: loaded && !composing && loadError !== ""
      ? "The thread may be out of date: " + loadError : ""

  Row {
    id: errorLine
    visible: root.sendError !== "" || root.staleError !== ""
    // same anchors as sendErrorLine
    spacing: 10
    Txt {
      width: parent.width - (retryStale.visible ? retryStale.width + 10 : 0)
      text: root.sendError !== "" ? root.sendError : root.staleError
      color: Theme.err; font.pixelSize: 12; wrapMode: Text.Wrap
    }
    OutlineButton {
      id: retryStale
      visible: root.sendError === "" && root.staleError !== "" && root.online
      icon: "refresh"; text: "Retry"; padX: 10; padY: 4; fontSize: 11
      onClicked: root.load(root.selected)
    }
  }
  ```

  The thread's bottom anchor (`:460`) follows `errorLine` as it followed
  `sendErrorLine`. The messages stay on screen.
- `load` already clears `loadError` when it starts (`:136`), so a
  successful retry or the next automatic reload removes the line.
- No automatic retry: the next conversation change already reloads
  (`:285`), and a timer would queue more work on the phone's single SMS
  thread (`SmsSync.kt:66`).

## Alternatives rejected

- **Sent intents on the phone** (real send results). Owner's answer to Q2:
  a follow-up, not this issue. It needs a new packet or field, and
  pending results across a restart of the app.
- **A wider slack, or no time check in live reports.** A live report can
  carry a watched older message whose type changed (`Sms.kt:244-272`), so
  an older message with the same text would clear a new entry
  (`sms_test.go:399-408`).
- **Matching by "newer than the newest message fluxd knew in the
  thread".** fluxd's list can be older than the phone's, so it rejects
  less than the clock and needs the same test change; the phone's clock is
  exact and costs one field.
- **A separate "Not confirmed" label for an entry with no report.** Dropped
  by the owner at the spec review: **Not sent** stays for both cases.
- **Ask the phone for the list on connect in fluxd.** Rejected in the
  intent (Q1): the page already asks, and it would double a full scan.
- **Automatic retry of a failed reload.** It adds work on the phone's one
  SMS thread when it is already slow. The Retry button and the next change
  are enough.
- **One report clears only one identical entry.** A report of the same
  message with a new type would then clear the second entry, which is
  worse. Two identical texts in a minute are rare; left as is.
- **MMS media.** Declined for now (Q4).
- **Ordering MMS in the same second.** MMS dates are whole seconds
  (`SmsSync.kt:372`), so two MMS in one second keep the phone's order
  under `sort.SliceStable` (`sms.go:201`). Item 3 is about desktop sends,
  which are SMS with millisecond dates; no change.

## Risks

- **The phone's clock in a packet.** `now` is read when the packet is
  built, and the packet can wait on the link for `D` seconds. Below the
  120 s threshold nothing changes. Above it, an older message with the
  same text can match if it is less than `120 + D` seconds older (see
  part 2); `D` is normally under a second.
- **A clock that jumps.** A jump ahead between the message and the packet
  leaves `behind` at 0: as today. A jump back by more than 120 s after the
  message was stored moves its time forward by the jump, so an older
  message with the same text could match. Both need a clock change within
  the 60 s of a send; accepted.
- **The capability check refuses a send that works today.** A phone that
  answers SMS but doesn't list `flux.sms.messages` would be refused. Flux
  for Android always lists both together (`Identity.kt:226-227`), and the
  window already hides Messages for such a phone. No other phone app sends
  SMS to fluxd.
- **A stale thread error that shows after the thread loaded again.** `load`
  clears `loadError` at its start, so the line goes on the next reload.
- **Layout on a narrow window.** The error row wraps its text; the
  Retry button takes its own width. The new view test checks it at 600 px
  as well as at the default width (Verification 3).
- **Part 5 changes.** Type 130 rows show a label until the MMS downloads;
  on AOSP the notice row is replaced by a new row, so the label goes on
  the next scan or reload. If the Pixel keeps the notice row after the
  download, the label could stay: the test checks this before the fix
  ships.
- **The #13 test setup.** The Pixel test uses the running fluxd and the
  Pixel. Installing the debug APK and running fluxd from the branch need
  the owner's OK first; p510 is not used.
