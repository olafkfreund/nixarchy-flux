# Intent: Install and configure Flux on NixOS with a flake

## Problem

Flux has no native, declarative way to install on NixOS. It ships an Arch
`PKGBUILD` (`dist/arch/PKGBUILD`), `make install` and `make install-user`,
and each assumes an FHS system:

- `make install` without `DESTDIR` writes `/etc/profile.d/flux-path.sh`
  and runs `dist/post-install.sh`, which writes `/etc/modprobe.d` and
  `/etc/modules-load.d`, loads v4l2loopback and restarts user services
  (`Makefile:58-78`, `dist/post-install.sh`).
- The code hard-codes FHS paths: the PAM helper at
  `/usr/lib/flux/flux-approve` (`internal/approve/pam.go:12`), `pam_exec.so`
  at `/usr/lib/security` (`cmd/flux/approve.go:177`), the polkit helper
  (`cmd/flux/approve.go:89`), the packaged user unit at
  `/usr/lib/systemd/user/fluxd.service` (`cmd/flux/setup.go:79`), and
  `/bin/kill` in `dist/fluxd.service`.
- `flux-cli approve enable` rewrites `/etc/pam.d/<service>` in place
  (`internal/approve/pam.go:123,282`), which fights NixOS's managed PAM files.
- `flux-cli setup` writes its own user unit when it does not find the
  packaged one, which can pin an old store path (`cmd/flux/setup.go:182`).
- `flux-cli update` installs a new release only through pacman, and
  otherwise tells the user to rebuild with `sudo make install`
  (`cmd/flux/update.go:60`). fluxd itself only notices a replaced binary
  and restarts (`internal/upgrade/upgrade.go:51`); it installs nothing.
- `flux-cli approve enroll` writes the user's phone key to
  `/etc/flux/approve` (`internal/approve/keyfile.go:21`), a run-time write
  to `/etc`.
- The omarchy-shell plugin must be real files, not symlinks
  (`cmd/flux/setup.go:315-328`, `plugin.ErrLinked`), and fluxd copies new
  plugin files into it after an update, so a Home Manager symlink tree
  under `~/.config/omarchy/plugins/flux` does not work.
- fluxd waits for transfers and streams to end before it restarts into a
  new binary (`internal/upgrade`); a `nixos-rebuild switch` that restarts
  the unit at once skips that wait.
- fluxd needs avahi over D-Bus for mDNS discovery (`internal/lan/mdns.go`),
  and calls about 25 external tools from `PATH` (pw-record, ffmpeg, wtype,
  mpv, gpu-screen-recorder, wf-recorder, hyprctl, omarchy-shell, xkbcli, …).

## Proposed outcome

On a NixOS (Nixarchy) machine a user adds this repo as a flake input and:

- `nix build .#flux` gives `fluxd`, `flux-cli`, `flux-approve`, `flux-gui`,
  the omarchy-shell plugin in the layout `omarchy plugin validate` accepts,
  the desktop entry and icons. The short name `flux` stays out of the main
  `bin/` (as the Arch package does), so it never hides fluxcd.
- `nix run .#flux-cli -- doctor` works without installing anything.
- A NixOS module (`services.flux.enable`) does declaratively what
  `post-install.sh` does today: the udev rule, avahi, and the firewall
  ports needed for discovery and connections. Webcam support
  (v4l2loopback) is a separate option, off by default, and never overrides
  a v4l2loopback config the host already has.
- fluxd runs only for the users the config names. A system that enables the
  module does not announce itself on the network for every account. Each
  user has one owner of the fluxd service, never two units.
- Fingerprint approval: the module adds the PAM line per named service
  (`security.pam.services.<name>`), off by default. `flux-cli approve
  enroll`, `status` and `remove` still work at run time, because they only
  manage the user's key. Only `approve enable`/`disable` refuse on Nix and
  point to the option.
- A Home Manager module enables fluxd and the omarchy-shell plugin for one
  user, installing the plugin as real files (as `flux-cli setup` does), and
  skipping it on desktops without omarchy-shell.
- A rebuild does not cut an active transfer: the unit is not restarted
  mid-switch, and fluxd's own restart-on-replace path is kept.
- `flux-cli update` on a Nix build says to update the flake input instead.
  `update --check` and `update --phone` keep working.
- Flux settings (`~/.config/flux`) stay user-managed; the modules do not
  generate them.
- `nix flake check` builds the package, runs the Go tests, and evaluates
  both modules. A manual smoke check on a Nixarchy desktop shows the GUI
  starts on Wayland and `flux-cli doctor` finds every tool it needs.

## Affected users and systems

- Users of this fork on NixOS / Nixarchy desktops (Hyprland, omarchy-shell).
- New files: `flake.nix`, `flake.lock`, `nix/` (package and modules).
- Small Go changes so the code finds its helpers in a Nix prefix and knows
  it was built by Nix (`internal/approve`, `cmd/flux`).
- Not affected: Android, iOS, macOS and Windows apps; the Arch package keeps
  working as today.

## Constraints

- Must keep the Arch/`make install` path working unchanged, so upstream
  changes keep merging cleanly. Go changes stay small and behind a build-time
  setting (an `-ldflags -X` value) instead of rewrites.
- Must not mutate the store, or `/etc` files NixOS manages, at run time.
  PAM changes go through `security.pam.services.*`. The enrolled-key
  directory `/etc/flux/approve` is user state: the module creates it (for
  example with `systemd.tmpfiles`), and it is not NixOS-managed.
- The PAM helper keeps its static build (`CGO_ENABLED=0`, `Makefile:30`),
  and the PAM line keeps its rule order and the refusal of `sshd`/`login`
  (`internal/approve/pam.go`).
- Building and checking locally (`nix build`, `nix flake check`) is part
  of verification. Switching a host, or any build on p510, is the
  owner's call; no deploy as part of this task.
- PAM approval is a `sufficient` auth rule: opt-in, off by default, per
  service.
- Must not make fluxd discoverable for users who did not opt in.
- `go.mod` needs Go 1.27.1; nixpkgs unstable has `go_1_27` (1.27.3).

## Decisions (approved 2026-11-11)

The owner approved the recommended answer to each question below.


1. Scope: Linux desktop only (daemon, CLI, Qt GUI, plugin), with the
   Android APK left to the existing Gradle build? Recommended: yes.
2. Modules: both a NixOS module and a Home Manager module, or NixOS only?
   Recommended: both. The NixOS module owns system parts (udev, avahi,
   firewall, PAM, v4l2loopback); the Home Manager module owns the per-user
   service and plugin. The NixOS module enables the service for its listed
   users only when Home Manager does not.
3. Should the security findings from the code review (symlinked browse
   roots, resumable transfers that skip the disk-space check, the empty
   release signing key) be fixed in this task or tracked as separate
   issues? Recommended: separate issues, so this task stays packaging.
