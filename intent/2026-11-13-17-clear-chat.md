# Intent: Clear the chat history on Android

## Problem

The Android app has no way to clear a computer's chat.
- The issue (mirrored from upstream `bjarneo/flux#161`) asks for it.
- Clips from a computer, such as a copied password, stay readable in the
  chat for anyone who picks up the phone.
- The desktop Flux app already has Clear and per-clip Delete. The phone
  doesn't match it.

### Facts

Paths are under `android/app/src/main/java/org/omarchy/flux/` unless they
start with `gui/`.

- **The chat log** is `SendLog` (`core/SendLog.kt:135-217`).
  - It is memory only. It keeps 60 finished entries (`MAX_SEND_LOG`,
    `SendLog.kt:65`) plus every running transfer, and cuts each text at 400
    characters (`SendLog.kt:68`).
  - It lives as long as the app process, which the foreground
    `FluxService` keeps running (`service/FluxService.kt:378`). In practice
    entries stay until the log rolls over.
  - It has no clear or remove function. `replace` swaps the whole list for
    the unit tests and the debug demo (`SendLog.kt:214-216`).
  - Every change goes through `_entries.update` (`SendLog.kt:143,176,195,200,206`),
    on the I/O threads of the transfers. Entry ids come from a counter that
    never resets (`SendLog.kt:136,148`); transfer callbacks find their entry
    by that id (`SendLog.kt:194-211`).
- **Running transfers.** `addSend` never drops an entry with
  `TransferState.Running` (`SendLog.kt:71-83`).
  - The chat's progress line is the sum of the running files
    (`ui/ChatScreen.kt:202,213-216`). A removed running entry drops out of
    it, and its later progress and end updates find nothing, so the chat
    loses the file's Done or Failed card.
  - A resumable transfer that no longer finds its entry starts a new one
    (`core/ResumableTransfer.kt:57-61`). So a deleted failed transfer that
    the computer retries comes back under a new id.
  - A resumable transfer stays `Running` between chunks
    (`ResumableTransfer.kt:104`). If the computer stops and never resumes,
    the entry stays `Running` until the app process ends. This is the case
    today; Clear would keep such an entry.
- **Where the log shows.** `rememberChatLog()` (`ui/ChatScreen.kt:146-151`)
  feeds:
  - a computer's chat, filtered by device (`ChatScreen.kt:196-197`);
  - the Chats list's last line per computer and its search
    (`ui/ChatsScreen.kt:104-108`, `core/ChatList.kt:119-123`).

  Both update when `SendLog.entries` changes. In a debug build with the
  demo on, `rememberChatLog()` adds sample entries that aren't in `SendLog`
  (`ChatScreen.kt:150`).
- **Open approvals** come from `Approvals.current`, not the log
  (`ChatScreen.kt:198-201`). A Clear leaves an unanswered request in place;
  only the Approved and Denied answers are log entries.
- **Incoming clips.** `InboxFeed.clipReceived` keeps the last clip as a
  `ClipEvent` with a 160-character preview and adds it to `SendLog`
  (`core/InboxModel.kt:216-234`). Callers: clipboard sync
  (`core/Plugins.kt:174`), shared text (`core/Share.kt:105-108`) and images
  (`core/ClipImage.kt:84`).
  - The UI reads `InboxFeed.clip` only for the computer's name on the
    dock's clip row (`ChatScreen.kt:1131`). Its preview is never shown.
  - So clearing `SendLog` removes every clip the chat thread shows.
- **The dock's clip row shows the phone's system clipboard**, not the log
  (`ChatScreen.kt:858,865,899-941,1125-1140`).
  - A password that a computer synced stays on the clipboard. The row shows
    it, up to 400 characters, as "Clipboard from <computer>", in the same
    chat, right under the cleared thread.
  - Flux writes it as plain text with label "Flux" and no sensitive flag
    (`core/Android.kt:138-143`). The row hides only clips that Android
    marks sensitive (`ChatScreen.kt:1134`).
  - The row's "Sent" state comes from a log entry with the same clip stamp
    (`ChatScreen.kt:901,941`). After a Clear it shows "Send" again.
- **Other copies that a Clear doesn't reach.** The full last remote text in
  `Plugins.lastRemoteClip` (`Plugins.kt:24,186`), a pending manual clip
  (`Plugins.kt:41`), the dock's cached read (`ChatScreen.kt:1099`), the last
  received clipboard image in the cache folder (`ClipImage.kt:71-85`), and
  system notifications for received links and files (`Share.kt:116`,
  `ResumableTransfer.kt:101`). All are memory, cache or the notification
  shade, not the chat.
- **The menu.** The chat's overflow menu is `ComputerMenu`
  (`ChatScreen.kt:244-269`): Control, Agents and terminals, New agent or
  terminal. A "Clear chat" item fits there.
- **Long press.** Outgoing text, link, scan and clip bubbles sit in a
  `SelectionContainer` (`ChatScreen.kt:699-708`), so a long press there
  already selects text.
- **Sample computers.** Other chat actions on a sample computer show "This
  is a sample computer" (`ChatScreen.kt:874,879`).
- **The desktop.**
  - The Chat page's "Clear history" button calls `clipboard.clear`. It
    empties the clipboard history of every device; saved (pinned) clips
    stay. It shows only when there is something to clear, and a toast
    confirms (`gui/qml/pages/Chat.qml:226-242`). File transfers are a
    separate list it doesn't touch (`Chat.qml:28-30`).
  - Each clip has a Delete icon, `clipboard.delete`, with no toast
    (`gui/qml/components/ChatEntry.qml:192-198`).
  - Neither asks for confirmation.
  - The phone has no saved clips, so it has nothing to keep.

## Proposed outcome

- A computer's chat has **Clear chat** in its overflow menu.
  - It shows only when that chat has something to clear.
  - It removes every finished and failed entry of that computer: links,
    text, clips, scans, files, and approval answers.
  - Running transfers stay, with their progress. Open approval requests
    stay.
  - The chat and the Chats list's line for that computer update at once,
    and search no longer finds the removed entries.
  - Other computers' chats stay.
  - If the phone's clipboard still holds the clip Flux put there from this
    computer, Clear chat empties the clipboard too (open question 4).
  - A short toast says what was cleared.
  - On a sample computer it shows "This is a sample computer".
- Each finished or failed entry has a **Delete** action that removes that
  entry only (open question 2). It doesn't break text selection.
- Entries that arrive after the Clear show as usual, including a failed
  transfer that the computer retries.
- Received files stay in Downloads. Notifications in the shade stay.
- Tests cover clear and delete, including running transfers kept,
  progress and end updates after a clear, a retried transfer, and the
  Chats list search.

## Affected users and systems

- Android users who sync clipboards or share text with a computer.
- `core/SendLog.kt` (clear and remove), `ui/ChatScreen.kt` (the menu item,
  Delete, the clipboard step), possibly `core/Android.kt` (empty the
  clipboard), and tests in `SendLogTest.kt` and `ChatListTest.kt`.
- Not affected: `fluxd`, the protocol, the desktop, iOS, macOS, Windows.
  The computer's own history is not cleared.

## Constraints

- Never drop a running transfer. Clear and remove act inside
  `_entries.update` and check the state there, so they can't lose a
  concurrent add, progress or resume.
- Entry ids stay unique: the id counter never resets.
- No new storage: the log stays memory only.
- No new permission.
- Never delete files in Downloads.
- Never empty a clipboard that holds something else than the clip Flux
  received from this computer.
- Text follows the house style of the app's other strings.

## Open questions

1. **This computer, or all computers?** Proposed: this computer only, from
   its chat's menu. Every item of that menu acts on one computer, and each
   entry carries one `deviceId`. An "all chats" action can come later on
   the Chats list if asked for.
2. **Per-entry Delete, and how?** Proposed: yes, in this issue. The issue
   asks for it ("or delete chats individually"), for one password among
   useful entries. A plain long press conflicts with text selection on
   outgoing bubbles (`ChatScreen.kt:702`), so the spec picks a way that
   keeps selection, such as a small menu on each entry or a long press on
   the entry's meta line.
3. **Ask before clearing?** Proposed: no dialog, as on the desktop. The log
   is memory only and short, and a toast confirms.
4. **Empty the phone's clipboard too?** Proposed: only when it still holds
   the clip Flux received from this computer, found the way the clip row
   already finds it (label "Flux" and `InboxFeed.clip` from this computer,
   `ChatScreen.kt:1131`). Otherwise the password the issue is about stays
   on screen in the clip row right after Clear chat. The toast says so,
   e.g. "Chat and clipboard cleared". A clipboard with anything else stays.
   Marking Flux's own clipboard writes as sensitive (`Android.kt:138-143`)
   is a separate issue.
5. **Stuck resumable transfers.** A resumable transfer that the computer
   abandoned stays `Running` and so survives Clear. Proposed: leave it for
   a separate issue; this one doesn't change transfer states.
6. **Test:** unit tests for clear and remove in `SendLogTest.kt` and the
   Chats list search in `ChatListTest.kt`. Then on the phone with the #13
   test setup:
   1. Sync a clip from the computer, start a large file, Clear chat. The
      clip is gone from the chat, the Chats list and the clip row; the
      file's progress continues and ends with its card.
   2. Another computer's chat is unchanged.
   3. Delete one entry; the others stay.
