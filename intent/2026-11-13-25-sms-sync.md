# Intent: Text messages on the desktop: missing messages, false "Not sent"

## Problem

Issue #25 mirrors upstream `bjarneo/flux#179`, reported on Flux 0.19.1.
It lists 5 problems with text messages on the desktop:

1. A message sent from the desktop shows **Not sent** in red, but the
   receiver got it.
2. Some messages that are on the phone never show on the desktop.
3. Messages sent from the desktop show out of time order.
4. MMS images, videos and voice messages don't show or play.
5. Conversations show numbers, not contact names.

Some of this changed after 0.19.1. The rest needs a cause before a fix.

### Facts

- **Upstream commit `f18a179`** "Show sent text messages once and in time
  order on the desktop" (`v0.19.1-6-gf18a179`) is in this branch. It
  changed:
  - outbox matching: by thread or by number, with other line ends, and
    any character where the sent text had a non-ASCII one, if the length
    matches (`internal/core/sms.go:377-417`);
  - a failed entry now goes at its time, a pending one at the end
    (`gui/qml/pages/Messages.qml:83-99`);
  - a message older than the last one now reloads the open thread
    (`sms.go:101-105,219-226`, `Messages.qml:280-285`), so it no longer
    stays hidden;
  - **Allow contacts** under Text messages when Flux can't read contacts.

  Sorting by time (`sms.go:199-201`) and contact names were already there.
- **"Not sent" has two meanings.** The same label (`Messages.qml:385,506`)
  shows for:
  - an outbox entry the phone didn't report in 60 s
    (`sms.go:33-36,316,350-363`); a later report removes it
    (`sms.go:365-375`, `docs/troubleshooting.md:287-289`);
  - a message the phone itself stored as failed, type 5
    (`sms.go:132-140`).
- **Why a sent message can miss the 60 s:**
  - The phone gets no send result: `SmsSync.send` passes `null` sent
    intents (`SmsSync.kt:185-189`). The phone's SMS table is the only
    report. When Android writes the sent row on a slow or multipart send
    is unverified.
  - The link drops after the send: the phone's scan finds no computer and
    moves on (`SmsSync.kt:238-244`). A later list refresh carries only the
    newest message per thread, so it may not include the sent one.
  - `SendSms` doesn't check that the phone offers text messages
    (`sms.go:284-318`, `api.go:472-473`); a send to a phone with the
    switch off waits 60 s and fails.
  - The phone's text differs in length from what was sent, for example a
    character changed into two (`sms.go:401-404`).
- **"Not sent" that never clears:** a report whose time is more than 120 s
  before the entry never matches (`sms.go:42-45,382`). Every report and
  every thread load uses the same check (`sms.go:229`), so the thread shows
  the real message and a "Not sent" copy until 50 newer sends push the
  entry out (`sms.go:38-40,330-332`) or fluxd restarts.
- **One report can clear several entries.** Two identical texts to one
  number are both removed by the first report (`sms.go:372-374`).
- **A retry after "Not sent" can send the text twice.**
- **Item 5 is implemented.** The phone adds contact names when Flux has
  contacts access (`SmsSync.kt:467-477`, `sms.go:120-124,155-158`,
  `docs/features.md:374-375`). Names are cached for 10 minutes
  (`SmsSync.kt:38`), and the desktop picks up a change when Messages
  opens again (`docs/troubleshooting.md:301-303`).
- **Item 4 is a feature.** An attachment is sent as a label such as
  `[Image]` (`core/Sms.kt:186-192`, `SmsSync.kt:389-408`), as documented
  (`docs/features.md:398`). No media bytes cross the link today.
- **Item 2, lasting causes in the code** (relevance to the reporter is
  unverified):
  - **RCS chats** are not in the SMS and MMS tables, so Flux can't read
    them (`docs/features.md:400`, `docs/troubleshooting.md:294`).
  - **MMS not yet downloaded.** Only MMS types 128 and 132 are read
    (`SmsSync.kt:53`). A download notice (type 130), for example with
    auto-download or mobile data off, shows on the phone but not on the
    desktop.
  - **Limits:** a thread loads its last 100 messages (`sms.go:256`); the
    phone lists 500 conversations and fluxd keeps 500 (`SmsSync.kt:29`,
    `sms.go:22,473-478`); a thread answer over 4 MiB drops its oldest
    messages without saying so (`Sms.kt:66-71,107-113`).
  - **One number in two threads.** The phone can keep 2 threads for 1
    number (`sms.go:377-380`). A reply sent from thread A can land in
    thread B; the desktop then shows it under another conversation with
    the same name, and not in A.
  - **MMS read errors are only logged.** A provider error drops all MMS of
    that read with a log line (`SmsSync.kt:257-263,292-293,301-306,317-321`).
- **Item 2, temporary gaps:**
  - **A thread reload that fails stays hidden.** When an open thread
    reloads and `sms.thread` fails or takes over 8 s (`sms.go:263-265`),
    the error shows only for a thread not yet loaded
    (`Messages.qml:121-150,515`). The thread stays old with no error and
    no retry until its conversation changes again.
  - **Messages that arrive while no computer is connected aren't pushed.**
    The scan moves its marks first (`SmsSync.kt:238-244,267-272`). The
    page asks for the list when it opens and when the phone comes online
    (`Messages.qml:295-304`), and the phone reads the list and threads
    without the marks (`SmsSync.kt:289-308`). So the page catches up.
    fluxd doesn't ask on connect (`internal/core/daemon.go:1183-1221`).
  - **The MMS mark at start** includes drafts and notices
    (`SmsSync.kt:216-228`), and **one scan sends at most 200**
    (`SmsSync.kt:32,267-273`). Both affect only live pushes; a reload shows
    the messages.
  - **MMS text that arrives later.** A watched message is sent again only
    when its type or read state changes (`Sms.kt:244-272`), so an MMS read
    before its text was stored can stay without text until a reload.
    Unverified on a device.

## Proposed outcome

- Item 2: the owner reproduces it on the Pixel with the current build
  and notes, for each missing message, its transport (SMS, MMS, RCS) and
  `adb logcat -s FluxSms` lines. Each confirmed cause is fixed, or
  documented when it can't be (RCS). Code bugs that a test can show,
  such as the hidden reload error, count as confirmed.
- Item 1: a message the phone sent does not stay "Not sent" on the
  desktop. A message with no report yet reads differently from one the
  phone says failed, so a user doesn't resend a message that went out.
- Items 3 and 5: the owner checks them on the Pixel. If they pass, the
  issue says which commit fixed what.
- Item 4: MMS media is declined for now, and the issue says why.
- Each item gets a recorded result in the issue after the owner's check.

## Affected users and systems

- Desktop users of Text messages with an Android phone.
- Possibly `android/.../core/SmsSync.kt` and `core/Sms.kt`,
  `internal/core/sms.go`, `daemon.go` and `api.go`,
  `gui/qml/pages/Messages.qml`, `gui/tests/tst_views.qml` (asserts the
  "Not sent" string), `internal/core/sms_test.go`, `flux-cli sms`,
  `docs/features.md` and `docs/troubleshooting.md`.
- Both desktop hosts share `Messages.qml`; no other host shows SMS.
- Not affected: iOS, macOS, pairing.

## Constraints

- Keep the protocol compatible: an older phone or fluxd still works.
- Keep `gui/qml/` working on both desktop hosts, and device state in
  fluxd (`AGENTS.md`). Keep the change small, so it can go upstream to
  `bjarneo/flux#179`.
- A phone-reported failure must still show as failed.
- No new Android permission. Contacts access stays optional.
- Reading RCS is out of scope: Android has no public API for it
  (unverified here; from Android's docs).
- The phone handles SMS requests one at a time on one thread
  (`SmsSync.kt:66,138-151`); a new request must not delay thread loads.
- Don't touch fluxd, adb devices or `/etc/flux` on the running #13 test
  setup without the owner's OK; p510 needs the owner's OK before any
  build or deploy.

## Open questions

1. **Item 2 scope: fix only what the Pixel test or a unit test
   confirms?** Proposed: yes. Fix the hidden reload error in any case.
   Don't add a list request on connect in fluxd: the page already asks,
   and a second request doubles a full table scan ahead of the thread
   load.
2. **Item 1: should the phone report the real send result (sent
   intents)?** Proposed: not in this issue. Separate "no report yet" from
   "failed" on the desktop and fix the clock and capability cases. Open a
   follow-up if the owner wants real results.
3. **Item 2: show MMS download notices (type 130) as a line such as
   "MMS not downloaded"?** Proposed: yes, if the Pixel test shows one;
   it is a filter and a label, not media.
4. **Item 4: decline MMS media for now?** Proposed: yes. It needs media
   transfer, size limits, a viewer and a player on both desktop hosts.
   Track it as its own feature issue if the owner wants it.
5. **Close #25 after this?** Proposed: close it when each item has a
   recorded result: fixed, documented or moved to its own issue.
6. **Test:** on the Pixel with the current build, logging
   `adb logcat -s FluxSms`:
   1. Send from the desktop 3 times, one over 160 characters and one with
      non-ASCII text; each shows once, in order, without "Not sent".
   2. With Messages open on a thread, disconnect, receive an SMS and an
      MMS, reconnect: both show. Repeat with Messages closed, then opened.
   3. Receive an MMS with auto-download off.
   4. Receive from a phone with RCS on; note the transport the Pixel's
      app shows.
   5. Turn contacts access off and on, then reopen Messages; names follow.

   Uses the #13 test setup that is still running, with the owner's OK.
