# Intent: A smaller Android APK

## Problem

Upstream's `flux-android-0.19.1.apk` is 71.2 MB. 58.6 MB of that (82%) is
native libraries, shipped for four ABIs: `arm64-v8a`, `armeabi-v7a`, `x86`
and `x86_64`. Almost all of it is ML Kit's text recognition
(`libmlkit_google_ocr_pipeline.so`) and barcode scanning
(`libbarhopper_v3.so`), pulled in by `android/app/build.gradle.kts:125-129`.

An `arm64-v8a` phone uses only 15.3 MB of those libraries. The rest is dead
weight on every update:

- `fluxd` downloads the whole APK into `~/.cache/flux/update/`;
- `flux-cli update --phone` sends the whole APK over Wi-Fi or the tailnet.

Since the fork's first release, v0.20.0, is what every phone and tablet
installs by hand (#44), this is the right time to fix it.

Facts from the code:

- **Flux is already arm64-only in practice.** The tailnet node
  `libflux_tsnet.so` is built only for `arm64-v8a`
  (`build.gradle.kts:22-31`, the default of `android/tsnet/build.sh`). On
  any other ABI, the APK installs but the tailnet node is missing.
- **The updater expects one APK.** `fluxd` looks for exactly
  `flux-android-VERSION.apk` (`internal/core/update.go:167,206`). The app
  does not report its ABI to `fluxd`, so `fluxd` cannot pick a per-ABI file.
- **The release builds and signs one APK.** The `apk` and `apk-sign` jobs
  (`.github/workflows/release.yml:74-190`) do this, and the certificate
  check, `SHA256SUMS` and the docs all name that one file.
- **Debug builds run on emulators.** `docs/android.md:321-460` uses an
  emulator (`emulator-5554`) for screenshots, which on an x86_64 computer
  runs an `x86_64` image.
- **The owner's device** connected over adb, a Pixel 11 Pro XL on API 37,
  reports only `arm64-v8a`.

## Proposed outcome

- The release APK `flux-android-VERSION.apk` contains native libraries for
  `arm64-v8a` only. It is about 26 MB instead of about 71 MB, so the
  download and the transfer to each phone are roughly 63% smaller.
- It keeps the same name and the same signing and checking path, so there
  is no change to `fluxd`, `release.yml` beyond what the build needs,
  `SHA256SUMS` or the first-install steps from #44.
- Debug builds keep `x86_64` as well, so the emulator workflow keeps
  working.
- The docs say that Flux for Android needs a 64-bit ARM device.

## Affected users and systems

- Every Android phone and tablet that installs v0.20.0 or later.
- `android/app/build.gradle.kts`: the ABI filter for release and debug.
- `docs/android.md` and `docs/install.md`: the device requirement.
- CI `build.yml`'s `android` job and the release `apk` job: same tasks,
  smaller output.
- Not affected: `fluxd`, the protocol, iOS, macOS, Windows.

## Constraints

- One APK per release with the existing name. `fluxd`, the release
  workflow and the #44 first-install steps depend on it.
- The 16 KB page alignment check in `release.yml:172-178` must still pass.
- `useLegacyPackaging = true` stays, because the tailnet node is run as an
  executable from the native library folder.
- The application ID, signing key and version code stay the same, so later
  updates install over v0.20.0.

## Open questions

1. **Is every phone and tablet that should run Flux 64-bit ARM?** The
   connected Pixel is. A 32-bit ARM device (`armeabi-v7a`) or an x86 Android
   device could not install the release any more. The tailnet node never
   ran on one anyway. Proposed: arm64 only. If a 32-bit device must stay,
   the alternative is `arm64-v8a` plus `armeabi-v7a`, at about 35 MB.
2. **ABI splits instead (the issue's approach)?** They would need several
   signed APKs, an ABI field from the app, and per-ABI selection in `fluxd`.
   Proposed: no, because arm64-only gets the same size with one config
   line.
3. **Other size cuts** (ML Kit's downloadable models instead of the bundled
   ones, or trimming `classes.dex`)? Proposed: out of scope; native
   libraries are 82% of the size.
