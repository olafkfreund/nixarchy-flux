# Intent: Control the phone from its screen mirror on the computer

## Problem

The screen mirror shows the Android phone in a window on the computer, but
the window only shows it.
- A click, a scroll or a key in the window does nothing on the phone.
- To use the phone, the user picks it up, even while its screen is on the
  computer in front of them.
- Upstream issue bjarneo/flux#184 asks for control, the way scrcpy does it
  over adb. It suggests Shizuku, so the phone can open adb on the local
  network itself.

### Facts

- **The mirror is pixels only, by design.**
  - The phone takes a `MediaProjection` (`screen/ScreenMirrorService.kt:135`)
    and draws an auto-mirror virtual display into an H.264 encoder
    (`ScreenMirrorService.kt:186-189`).
  - The `flux.screen` packets carry a port and a frame size from the phone,
    and only "live", "error" or "stop" back. The protocol comment says "The
    computer only shows the screen" (`screen/ScreenProtocol.kt:9-46`).
  - `fluxd` pipes the stream into mpv or ffplay and "sends no input to the
    phone" (`internal/core/screen.go:15-17,65-93,216-217`). The user docs
    say the same (`docs/camera.md:328-329`).
  - The window is that player. It has no way to hand clicks back to
    `fluxd`, and the Hyprland rule keeps it from taking the keyboard focus
    (`docs/camera.md:338-339`).
  - The phone asks for capture with a plain `createScreenCaptureIntent()`
    (`ui/ControlScreen.kt:208`), so on Android 14+ the user may share a
    single app. The frame size still comes from the whole default display
    (`ScreenMirrorService.kt:238-243`). With a single app or a `FLAG_SECURE`
    app, the window would not show what a touch lands on.
- **Why control is impossible today.**
  - `MediaProjection` gives an app pixels, not input.
  - Injecting touches into other apps needs `INJECT_EVENTS`, a
    signature permission an ordinary app can't get. The shell uid of adb
    has it, which is how scrcpy works.
  - The other way for an app is an `AccessibilityService` with
    `dispatchGesture`, which sends touch gestures but not text. Flux
    declares no such service: its services are the Flux service, the
    mirror, the streams, a tile and the notification listener
    (`android/app/src/main/AndroidManifest.xml:155-191`).
- **Control already runs the other way.** The phone can drive the
  computer's pointer and keyboard, and see its screen. Both are off by
  default, because the phone could then type in any window
  (`internal/config/config.go:57-63`, `docs/remote-input.md:5-8`,
  `docs/security.md:75-76`). "The computer does not control the phone or
  the Mac" (`docs/remote-input.md:6`).
- **The screen mirror has no setting.** It is on for every paired phone, and
  the phone starts it after Android's capture prompt (`docs/security.md:77`).
- **What a user can do today, outside Flux.**
  - Android 11+ **Wireless debugging** plus scrcpy already gives streaming
    and control. Flux's docs already use `adb pair` and `adb connect` to
    install the APK (`docs/android-setup.md:60-69`, `docs/android.md:17-20`).
  - **Shizuku** runs a helper with the shell uid. Without root it must be
    started through Wireless debugging or a cable, and again after each
    reboot.
  - Both are in nixpkgs (`scrcpy` 5.0.1, `android-tools` 37.0.0p1, from
    `nix eval nixpkgs#<name>.version` on 2026-11-15). Neither
    is in Flux's runtime packages (`nix/nixos.nix:30-46`,
    `nix/home-manager.nix`), and `flake.nix` names neither.
- **Security cost of each path.**
  - adb gives the computer a shell on the phone: it can install apps, read
    shared storage, grant permissions and inject any input. SELinux and
    Android permissions still keep it out of other apps' private data. That
    is far more than any Flux feature grants today.
  - Wireless debugging (Android 11+) listens on the Wi-Fi network, but a new
    computer must pair with a code from the phone. A computer whose adb key
    the phone has authorized keeps access until the user revokes it, or
    Android's authorization timeout drops it. The older `adb tcpip` mode,
    which Shizuku or a shell can turn on, has no pairing code; it asks on
    the phone the first time a key connects, and its traffic has no TLS.
    `docs/android-setup.md:73` notes that Samsung's Auto Blocker can also
    block adb.
  - On the computer, adb's key is a file in the user's home. Any process of
    that user can use it, outside `fluxd`'s settings and outside unpair.
  - An app that uses Shizuku gets the whole shell uid, not only input.
    Starting Shizuku through Wireless debugging leaves Wireless debugging
    on until the user turns it off.
  - That adb trust is separate from Flux's pairing and pinned certificates
    (`internal/config/trust.go:34`, `docs/security.md:14-54`). An unpair
    ends every Flux session (`docs/security.md:219-235`), but it would not
    revoke an adb key.
  - An `AccessibilityService` can see and act on what apps show, as far as
    its declared capabilities allow. Android 13+ restricts such access for
    apps installed from a browser or a file manager, the same mechanism
    `docs/android-setup.md:86-106` describes for notification and SMS
    access, which on Android 15 can apply to adb installs too. Unlike the
    capture consent, an enabled accessibility service stays on across
    reboots until the user turns it off. Intent #56 ruled out adding one
    (`intent/2026-11-13-56-air-command-approve.md:89-90`).
- **Flux treats a tap on the phone as consent.** The phone never starts its
  camera or microphone without a tap on the phone (`docs/security.md:128`).
  Approve, Pair and SSH signing also need a tap, and the screen lock can
  sign SSH requests (`docs/security.md:141-142`). Code that runs as the
  user on the computer "can send requests to the phone, but it cannot sign
  without your approval" (`docs/security.md:146`). Input from the computer
  could tap those screens, and type a screen lock it has seen. The
  tapjacking guard of #56 would likely not catch injected taps (unverified).

## Proposed outcome

The smallest useful version:
- A user with a paired Android phone can tap, swipe, scroll and type on the
  phone from its mirror window on the computer.
- Control is off until the user turns it on (where the switch lives is
  question 3). It is for one named computer and one mirror session.
- Control stops at once when the user turns it off, the mirror stops, the
  link drops, or either side unpairs. Nothing from that session keeps
  access to the phone.
- The phone always shows that it is being controlled, and the user can stop
  it from the phone.
- Viewing only stays as it is today, with no new setup, for users who don't
  turn control on.
- `docs/camera.md` and `docs/security.md` say what control grants, what it
  costs, and how to turn it off.

Out of scope:
- Starting the mirror from the computer: Android's capture prompt stays a
  tap on the phone.
- Multi-touch, pinch, stylus pressure, and control while the phone screen
  is off.
- iOS and the Mac: iOS has no screen mirror (`docs/ios.md:311-318`).
- Phone audio, clipboard and file transfer through the mirror. Flux has its
  own features for those.
- Control over Remote access (Tailscale) or other networks beyond the local
  one, unless the owner decides otherwise below.
- Root-only methods.

## Affected users and systems

- Android users who mirror the phone to an Omarchy or NixOS computer.
- Depending on the path chosen: `screen/` and the manifest on Android,
  `internal/core/screen.go`, the `flux.screen` protocol, the mirror window,
  the GUI's Access card, `dist/hyprland.lua` (the window's focus rule),
  and the Nix runtime packages.
- Docs: `docs/camera.md`, `docs/security.md`, `docs/android-setup.md`,
  `docs/remote-input.md`.
- Not affected: iOS, macOS, Windows, and the phone-to-computer remote input.

## Constraints

- No control without an explicit opt-in on the phone. A paired computer must
  not gain control by itself.
- Flux must not leave adb or Wireless debugging open on the network after
  control stops, and must not open adb on an interface the user did not
  choose.
- No new trust that outlives an unpair or a stop. A path that leaves an
  authorized adb key behind breaks this, unless the owner accepts it in
  question 1.
- No input reaches the phone unless a mirror of the whole screen is live
  to that computer. No input in the background.
- Input from the computer must not grant or extend its own access: no
  turning control on, pairing a computer, approving a Flux request, or
  allowing a permission prompt. Flux's own consent screens keep needing a
  person at the phone.
- No root.
- Keep the current mirror working for phones and computers without the new
  feature, and keep old `fluxd` and old apps compatible.
- No adb against the owner's devices in agent runs; device tests are the
  owner's.

## Open questions

1. **How much privilege is acceptable?** Proposed: the owner sets the
   limit here, and the spec picks the mechanism within it. The candidates
   and what each costs:
   - **a. Just launch scrcpy.** `fluxd` or the docs start scrcpy for a
     phone the user has already paired over Wireless debugging. Least code;
     full shell trust; a second pairing outside Flux.
   - **b. adb via Shizuku, Flux's own stream.** The app uses Shizuku's
     shell uid to inject input it gets over Flux's TLS link. Needs Shizuku
     installed and restarted after each reboot; the computer needs no adb.
   - **c. AccessibilityService.** Touch gestures through
     `dispatchGesture`, over Flux's link. No adb, but broad access to what
     apps show, the restricted-settings step, and Home and Back only as
     global actions. Typing text needs another mechanism. Whether it adds
     Play Protect warnings for the whole APK is unverified.
2. **Network exposure.** If adb is in the path, may Wireless debugging stay
   on while the mirror runs, or must Flux keep adb off the network (only
   Shizuku's local binder, or a cable)?
3. **Default and switch.** One switch on the phone, or one on each side like
   `remote_input`? A switch in the computer's `config.toml` can't protect
   the phone; only the phone can. Should control need the phone's screen
   lock or biometric first, like the touchpad and the remote desktop
   (`docs/security.md:93`, valid 5 minutes per `docs/remote-input.md:43`)?
4. **Scope of input.** Touch and text only, or also the Back, Home and
   Recents keys and the volume keys? Without Back and Home, edge swipes of
   gesture navigation may be hard from a window.
5. **Approval screens.** The constraints say Flux's own Approve, SSH
   signing, Pair and stream request screens refuse input from the computer.
   Confirm, or make control and approval on one phone the user's choice?
   Proposed: confirm.
6. **Lock screen and system prompts.** May the computer unlock the phone
   with a typed PIN, and act on Android's permission and capture prompts?
   Proposed: no; the user does those at the phone.
7. **Test:** on the owner's phone, with the owner present: mirror, turn on
   control, tap, swipe and type into an app; turn it off from the phone and
   check the window input stops; unpair and check control stops.
